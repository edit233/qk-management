## CI/CD 工作流搭建

用户要求分析项目并编写 GitHub Actions 实现自动构建、测试、部署。

### 项目架构识别
- 后端：Spring Boot 3.5.16 + Java 21 + Maven 多模块（qk-parent → qk-common/qk-entity/qk-management）
- 前端：Nginx 1.24 + 纯静态 HTML/JS/CSS
- 数据库：MySQL 8.0（仅运行时需要，不参与 CI/部署流程）
- 对象存储：阿里云 OSS
- 部署：Docker Compose，3 服务（backend / frontend / mysql）

### 产出文件
- `.github/workflows/ci.yml` — PR/push 触发：编译 + 单元测试 + 镜像构建验证（无 MySQL 依赖）
- `.github/workflows/release.yml` — tag 触发：构建推送镜像到 GHCR（可选 ACR）
- `.github/workflows/deploy.yml` — 手动触发：SSH 调用服务器侧脚本，不接触业务密钥
- `.dockerignore` — 优化 Docker 构建上下文
- `scripts/deploy.sh` — 服务器侧部署脚本（读本地 .env，失败回滚）
- `.env.example` — 密钥字段模板（提交到 git，作为"密钥备份说明"）
- `docs/DEPLOY.md` — 部署配置指南：含密钥清单、首次部署、回滚、密钥重建流程

### 关键设计原则（用户强调）
1. **MySQL 不做自动化部署**：CI 移除 MySQL service，部署脚本不包含 DB 容器
2. **业务密钥全部留在服务器本地 .env**：GHCR_TOKEN / DB / OSS 都不进 github
3. **GitHub Actions 只通过 SSH 触发**：4 个 secret 全部是部署机访问（HOST/USER/SSH_KEY/PORT）
4. **密钥清单作为文档提交**：.env.example + docs/DEPLOY.md 提供完整字段说明，重建 .env 时无需记忆

### 技术栈要点
- JDK 21（Eclipse Temurin）
- Maven 用阿里云镜像（pom.xml 已配置）
- GHCR 免费且原生集成 GITHUB_TOKEN
- appleboy/ssh-action@v1 用于 SSH 远程执行
- 镜像标签：tag + latest + 时间戳 三种

## 后端 application.yaml 配置重构

用户痛点：application.yaml 写死了 root/123456，OSS 用 `${}` 占位符必须从外部 env 注入；IDEA 本地测试不方便。

方案演进：
1. 第一次尝试：激进的多 profile（application-local.yaml / application-prod.yaml + .example 模板 + gitignore）。问题：开发者要 cp .example 一次，多文件难维护。

## CI/CD 流水线整合（push-to-deploy）

用户反馈：之前分散的 CI/CD 流程（ci.yml + release.yml + deploy.yml + docs/DEPLOY.md）步骤太多，要求合并为"一条流水线"，**git push 后自动完成构建 + 部署**。

### 改造方案

**删除**：
- `.github/workflows/ci.yml`（PR/push 编译测试）
- `.github/workflows/release.yml`（tag 触发推镜像）
- `.github/workflows/deploy.yml`（手动触发 SSH 部署）
- `docs/DEPLOY.md`（合并到主 README）
- `docs/LOCAL_DEV.md`（合并到主 README）
- 整个 `docs/` 目录

**新建 / 改造**：
- `.github/workflows/pipeline.yml`（**唯一** CI/CD 配置，3 个 job 串成一条线）：
  - ① build-test：编译 + 单元测试 + 打包 jar
  - ② build-push-image：构建 + 推送镜像到 GHCR（推镜像 + tags: <ref-sha> / latest / <run#>）
  - ③ deploy：SSH 到服务器执行 deploy.sh，env 解析（main→prod / dev→dev）
- `scripts/deploy.sh`：简化，兼容公开 GHCR（无需 docker login）
- `.env.example`：去掉强制的 GHCR_TOKEN，改为可选
- `README.md`：完全重写，以"流水线"视角组织（§1 系统要求 / §2 首次部署 / §3 日常使用 / §4 数据库 / §5 运维 / §6 Git / §7 本地开发 / §8 故障排查 / §9 安全 / §10 流水线参考）

### 流水线触发规则

| 事件 | 行为 |
|------|------|
| PR → main/dev | 仅 ① 编译测试 |
| push → main | 全流程，部署到生产（DEPLOY_HOST_PROD） |
| push → dev | 全流程，部署到开发（DEPLOY_HOST_DEV） |
| push tag v*.*.* | 全流程，部署到生产 |
| workflow_dispatch | 全流程，可指定 ref |

### 镜像标签策略

- main: `main-<sha>` + `latest` + `<sha>-<run#>`
- dev: `dev-<sha>` + `<sha>-<run#>`
- tag v1.0.0: `v1.0.0` + `latest` + `<sha>-<run#>`

### 关键设计

- GHCR 包设为 public 后，服务器无需 GHCR_TOKEN
- 业务密钥（DB/OSS）仍在服务器 `.env`，通过 deploy.sh 注入到 docker-compose.yml
- GitHub Secrets 只有 5 个，全是部署机访问信息（HOST_PROD/HOST_DEV/USER/SSH_KEY/PORT）
- 用户日常只需 `git push`，无需 SSH 服务器

### 设计原则

- ✓ 单一 workflow 文件（pipeline.yml），流程可视化
- ✓ 所有文档合并到主 README，零文档跳转
- ✓ 服务器只 pull 镜像，不做 git 操作
- ✓ 业务密钥严格隔离在服务器本地
